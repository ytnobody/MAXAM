# ワークフロー

MAXAMのエージェント間連携ワークフローについて詳しく説明します。

## 基本フロー

```
ユーザー → Mei（要件整理）→ Yuki/Rin（実装）→ Shiori（テスト）→ Priya（レビュー）
               ↑                                                      │
               └─────────────────── フィードバック ───────────────────┘
```

## レビューサイクル

`maxam review` で実行される自動レビューワークフローです。

### 動作フロー

```
┌─────────────────────────────────────────────────────────────┐
│                    レビューサイクル                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. タスク受付                                               │
│     └─→ Yuki（developer）が実装                             │
│                                                             │
│  2. レビュー                                                 │
│     └─→ Priya（reviewer）がチェック                         │
│                                                             │
│  3. 判定                                                     │
│     ├─→ APPROVED → 完了                                     │
│     ├─→ [MINOR] → 修正 → 再レビュー（ラウンド2へ）          │
│     ├─→ [DESIGN] → エスカレーション                         │
│     ├─→ [REQUIREMENTS] → エスカレーション                   │
│     └─→ [SEC-CRITICAL] → 即時エスカレーション               │
│                                                             │
│  ※ 最大3ラウンド後もApproveされない場合はエスカレーション   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### レビュータグ

| タグ | 意味 | 対応 |
|-----|------|------|
| `APPROVED` | 問題なし | 完了 |
| `[MINOR]` | 軽微な問題 | 実装者が修正して再レビュー |
| `[DESIGN]` | 設計レベルの問題 | Meiにエスカレーション |
| `[REQUIREMENTS]` | 要件が不明確 | Meiにエスカレーション → 顧客確認 |
| `[SEC-CRITICAL]` | セキュリティ重大 | 即時ブロック、Meiにエスカレーション |

### ラウンド制限

- **最大3ラウンド**の修正 → 再レビューが可能
- 3ラウンド後もApproveされない場合は自動エスカレーション
- 無限ループを防ぎ、人間の判断を促す

### モデル選択

レビューサイクルでは、ラウンドに応じてモデルが自動選択されます：

| ラウンド | 変更規模 | 使用モデル |
|---------|---------|----------|
| 1 | - | デフォルト（Sonnet） |
| 2+ | 100行以下 | Haiku（高速・低コスト） |
| 2+ | 100行超 | デフォルト（Sonnet） |

### 使用例

```bash
maxam review "Create unit tests for the auth module"
```

出力例：

```
MAXAM Review Cycle
==================
Task: Create unit tests for the auth module

=== Round 1 ===
[yuki] Implementing...
[yuki] Done (2.3s)
[priya] Reviewing...
[priya] Done (1.1s)

=== Summary ===
Status: APPROVED
Iterations: 1
```

## 分析サイクル

`maxam analyze` で実行される分析ワークフローです。

### 動作フロー

```
ログ蓄積 → Amara分析 → レポート生成 → 改善提案
```

### トリガー条件

分析は以下のタイミングで実行されます：

| トリガー | アクション |
|---------|----------|
| PRマージ時 | パターン抽出 → 学習事項更新 |
| 差し戻し発生時 | 原因分析 → 再発防止策検討 |
| 手動実行 | `maxam analyze` |

### 最小メッセージ数

分析を実行するには、一定数以上のログが必要です：

```yaml
# config.yaml
analysis_min_messages: 10  # デフォルト
```

### 出力

```
MAXAM Weekly Analysis
=====================

=== Analysis Report ===
今週の主な活動:
- PRマージ数: 12
- レビュー差し戻し: 3回
- エスカレーション: 1回

パターン:
- 認証関連のPRでレビュー指摘が多い
- テストカバレッジが低い傾向

=== Recommendations ===
1. 認証モジュールのテストを強化
2. コードレビューチェックリストの導入を検討
3. ...
```

## エスカレーションフロー

問題が発生した場合のエスカレーションルールです。

### エスカレーション条件

| 条件 | 対応 |
|------|------|
| 同一PR差し戻し3回超過 | PMへエスカレーション |
| `[SEC-CRITICAL]` タグ | 即時ブロック、PMへ |
| 要件不明確 | PMへ → 顧客確認 |

### 原則

> **下流で無理に解決しない。問題は上流に伝播させる。**

実装者が設計問題を無理に解決しようとすると、かえって問題が複雑化します。
適切なタイミングでエスカレーションすることで、効率的に問題解決できます。

## チームチャットでの連携

TUIチャットでは、エージェント間で自然に連携できます。

### メンションによる協調

```
You: ログイン機能を作りたい

Mei: いいですね！いくつか確認させてください：
     1. 認証方式は？
     2. ...

You: JWTでお願い

Mei: 了解です。@yuki、JWT認証の実装お願いできる？

Yuki: 了解。作業入る。
```

### タスクボード連携

チャット内で `Tab` キーを押すとタスクボードを表示できます。
タスクの進捗を確認しながらチャットできます。

## ワークフローのカスタマイズ

### ロールの割り当て

`config.yaml` でロールを設定することで、レビューサイクルで使用されるエージェントを変更できます：

```yaml
agents:
  - name: alice
    full_name: Alice Developer
    role: developer
  - name: bob
    full_name: Bob Reviewer
    role: reviewer
```

### 最大ラウンド数

現在、最大ラウンド数はコード内で固定（3ラウンド）されています。
将来的に設定可能になる予定です。
