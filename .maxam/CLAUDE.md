### 1. 設計パターン

#### フォールバックパターン
- 設定優先 → なければデフォルト値
- 既存動作を壊さない安全な拡張
- 例: `omitempty`で後方互換維持、「空なら何もしない」

#### 段階的実装
- フェーズ分けで効果が得られる部分から実装
- nice to haveも優先度を切り分け、全部やらない勇気を持つ
- 先読み実装はスコープが明確な場合のみ（方針変更リスクあり）

#### エラーハンドリング
- バックグラウンド処理はベストエフォートで設計
- 多重防御パターン: 段階的に実行し確実性を担保
- 親切なエラーメッセージ: 「何が問題か + どうすればいいか」を1セットで

#### テスト設計
- パターンごとにグループ化（カバレッジが一目で分かる）
- 環境依存テストは `t.Skip()` で明示的にスキップ
- グローバル状態に依存しない設計（`t.TempDir()` + 環境変数オーバーライド）

#### 状態マシン設計
- 複雑なワークフローは状態遷移で表現
- 状態は明示的なenumで定義（`StateIdle`, `StateWaitingApproval`等）
- `sync.RWMutex`で並行安全性を担保
- 参考: PR #172（自動プランモード）

#### ポーリング設計
- 間隔はハードコードせず設定可能に
- デフォルト値は`Config`構造体で管理
- `context.Context`でキャンセル可能に
- 参考: PR #172（承認監視機能）

#### ヘルスモニタリングパターン
- `Monitor` struct + `HealthChecker` interface の組み合わせで拡張性確保
- 定期監視ループは goroutine + ticker で実装
- 失敗閾値（consecutive failures）超過で自動復旧トリガー
- graceful shutdown は `context.Context` + `done` channel で実現
- interface 分離により、テスト時のモック差し替えが容易
- 参考: PR #344（ヘルスモニタリング機能）

#### 自動リセット設計
- **クールダウン30秒**: LLMタイムアウトは一時的なことが多く、30秒で自然回復を待てるバランス点
- **しきい値3回**: 連続3回失敗で「一時的ではない問題」と判定、PMへエスカレーション
- クールダウン30秒 × 3回 = 約1.5分で判定完了（CLAUDE.mdの15分ルールより早い初動）
- `IsRecoverableError()` で対象エラーを判定し、無関係なエラーには反応しない
- 参考: Issue #361, PR #364

### 2. チームフロー

#### 報告フォーマット
**実装完了報告:**
1. 実装コードの要点
2. テストケース数とカバー範囲
3. テスト実行結果
4. 統合状態（例：「TUIに組み込み済み」）
5. 全機能を列挙（追加したコマンド、API等）

**調査タスク報告:**
1. 調査結果
2. 結論（できる/できない、推奨事項）
3. 次のアクション

#### GitHubアカウント制約
- オーナーPRは同一アカウントでApprove不可
- 軽微な変更はレビュアーLGTM確認後、オーナー判断でマージ

#### タスク管理
- タスク状況はGitHubから自動取得（TUIステータスバーに表示）
- 「○○やります」と明示してから着手
- CI待ち時間を活用してスコープ確認
- **PR提出前にローカルでCI相当のチェック実施**（gofmt, go vet, テスト）

#### オーナーとチームの役割
- オーナー＝意思決定者（確認・判断をする人）
- 技術的操作（ビルド、git、テスト）はチームが担当
- 「手順を伝える」より「やっておく」が適切

#### エラー発生時のフォロー
1. PMがエラー検知したら即座に声かけ
2. 復帰確認
3. 復帰しなければ再割り当て

#### レビューフロー遵守
- **全PRはレビューを通す**（軽微な変更でも例外なし）
- 軽微な変更はレビュアーがレビュー＆即マージOK
- フロー逸脱は週次で可視化し、原因を振り返る

#### PRクローズ時のコメント
- マージせずクローズする場合、必ず理由をコメントに残す
- 例: 「#XXX に統合」「方針変更により不要」「実装アプローチ変更」

### 3. アンチパターン

#### 「How」と「What/Why」の混同
> 「実装できる」と「正しく設計されている」は別

**機能設計時のチェックリスト:**
- [ ] この機能は誰向けか？（オーナー / エージェント / 両方）
- [ ] この機能で何を達成したいか？（目的）
- [ ] この機能がないと何が困るか？（課題）
- [ ] 確認が必要な場合、オーナーに質問したか？

**教訓:**
> 「情報を出す側」は常に「誰がこれを知るべきか」を考える

#### 検証なし報告（v0.12.1 ビルド問題より）
- 「ビルド完了」と報告したが、実際には `VERSION` が埋め込まれていなかった
- Makefileの `-ldflags="-X main.Version=$(VERSION)"` の仕組みを理解せずに報告
- **根本原因**: 「やった」と「正しくできた」の混同

**教訓:**
> 報告前に必ず結果を実確認する。`./bin/maxam --version` 等で期待値と一致するか検証。

#### レビューなしマージの常態化
- 直近20件中7件（35%）がレビューなしでマージ
- 速度優先でフロー逸脱、「軽微な変更」の判断基準が曖昧

**データ（該当PR）:**

|----|------|
| #244, #243, #235, #233, #224, #220, #218 | レビューなしマージ |

**教訓:**
> CLAUDE.mdにルールがあっても忙しいと無視される。フロー違反は定期的に可視化すべき。

#### PRクローズ時の理由未記載
- #231, #232 がCLOSEDだが理由が不明
- 後から追跡できない

**教訓:**
> CLOSEDの理由を必ずコメントで残す。「別PRに統合」「方針変更で不要」等。

### 4. 環境・ツール

#### Goインストール（Ubuntu）
```bash
# シンプル
sudo apt update && sudo apt install -y golang-go

# 最新版が必要な場合
wget https://go.dev/dl/go1.23.5.linux-amd64.tar.gz
sudo rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go1.23.5.linux-amd64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc
```

#### Makefile設計
- `PLATFORMS`リストを宣言的に管理
- `dist`（単一）と`dist-all`（一括）の2段階設計
- `-ldflags="-s -w"`でバイナリサイズ削減
- バージョンは`git describe --tags --always --dirty`で自動取得

#### GitHub Actions
- イベント設計: `pull_request.closed` + `merged == true`
- 最小権限原則: 必要以上の権限を付与しない
- `GITHUB_TOKEN`を活用しセットアップコスト低減

#### レビュアー（Priya）不在時のフォールバック（#336 の経験より）

Priyaが応答不能になった場合の対応ルール：

1. **軽微な変更**（typo、ドキュメント、テスト追加）
   - Shiori または他メンバーが簡易レビュー＆即マージOK
   - セキュリティチェックリスト確認後、問題なければ進める

2. **セキュリティ関連**（`[SEC]`タグ）
   - Priya復帰まで待機
   - 緊急度が高い場合のみMei判断でエスカレーション

3. **復帰後の報告**
   - 対応状況をサマリで共有
   - 必要に応じて追認レビュー

**運用の背景：**
Priyaの無反応が数分続く場合、技術的問題（context deadline等）の可能性がある。待ちながら監視するより、軽微な変更は別メンバーで進め、並行して復帰確認する方が効率的。
