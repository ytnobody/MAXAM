```bash
# 方法1: aptでインストール（シンプル）

sudo rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go1.23.5.linux-amd64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc
source ~/.bashrc
go version

# 動作確認
cd /tmp/maxam/priya/MAXAM
go test ./...
```

#### 報告フォーマット

**実装完了報告**には以下を含める:
1. 実装コードの要点
2. テストケース数とカバー範囲
3. テスト実行結果

**調査タスク報告**には以下を含める:
1. 調査結果（何を調べ、何が分かったか）
2. 結論（できる/できない、推奨事項など）
3. 次のアクション（必要な場合）

- 報告の詳細度が上がるとレビュー品質も向上する傾向

#### GitHubアカウント制約
- オーナーアカウントで作成したPRは、同一アカウントではApproveできない
- 軽微な変更（ドキュメントのみ等）はレビュアーのLGTM確認後、オーナー判断でマージ可

#### タスク実行の重複防止
- 同一タスクを複数エージェントが拾わないよう、作業開始時に宣言する
- 「○○やります」と明示してから着手

### 2026-01-30 分析結果 (by Amara)

#### クロスコンパイル対応（PR #62より）
- Makefileで `PLATFORMS` リストを宣言的に管理し、`dist-all` で一括ビルド
- `-ldflags="-s -w"` でバイナリサイズ削減（デバッグ情報除去）
- バージョンは `git describe --tags --always --dirty` で自動取得、タグなければ "dev"
- 配布パッケージにはバイナリ + 設定ファイルを含め、解凍即使用可能な状態に

#### Makefile拡張のパターン
- 既存ターゲット（build, test, clean）に影響を与えず新機能追加
- `dist`（単一）と`dist-all`（一括）の2段階設計で柔軟性確保
- 対象プラットフォームをリストで宣言的に管理（linux/amd64, darwin/amd64, darwin/arm64, windows/amd64）

#### GitHub Actions自動トリガーの設計パターン（PR #69より）
- **イベント設計**: `pull_request.closed` + `merged == true` の組み合わせでマージ時のみ発火
- **最小権限原則**: `pull-requests: write` のみで運用、必要以上の権限を付与しない
- **外部シークレット不要**: `GITHUB_TOKEN` を活用しセットアップコスト低減
- ワークフローファイル1つ、24行で実現（シンプルに保つ原則に沿う）

#### 段階的実装の判断例（PR #69より）
- フェーズ1（通知トリガー）とフェーズ2（自動検出ロジック）を分離
- 「まず効果が得られる部分だけ実装」という判断で効率的にデリバリー
- nice to haveの中でも優先度を切り分け、全部やらない勇気を持つ

#### 先読み実装のパターン
- 方針決定前にYukiが実装を先行着手、結果的にスムーズな流れに
- リスク: 方針変更時に手戻りが発生する可能性あり
- 適用条件: スコープが明確で大きな方針変更が予想されない場合に限る

#### 設定拡張の好例（PR #74）
- 構造体フィールド1つ + `omitempty`で後方互換維持
- 引数追加時は既存テストも漏れなく更新
- オプショナル機能は「空なら何もしない」パターンで安全に実装

#### コンテキストモード切り替え機能（PR #82より）

**変更規模:** 5ファイル、+285/-3行、テスト9ケース追加

**設計パターン:**
1. **型安全な設定** - `ContextMode`型を定義（`full`/`summary`）、マジックストリングを排除
2. **グレースフルフォールバック** - `CLAUDE.summary.md`がない場合は自動的に`CLAUDE.md`を使用
3. **多段階のコンテキスト読み込み** - プロジェクト用とエージェント用、両方にフォールバックを適用

**トークン削減効果:**
- `CLAUDE.summary.md`: 81行（元の`CLAUDE.md` 400行から約80%削減）
- 要約版は「チームが知っておくべき最小限」に絞り込み

**実装の好例:**
```go

if data, err := os.ReadFile(sharedPath); err == nil {
    parts = append(parts, string(data))
} else if r.ContextMode == config.ContextModeSummary {
    // Fallback to full version if summary not found
    sharedPath = filepath.Join(r.WorkDir, "CLAUDE.md")
    // ...
}
```

**使い方:**
```yaml

context_mode: summary  # or "full"（デフォルト）
```

#### CLIサブコマンド設計の好例（PR #113より）

**変更規模:** 4ファイル、+483行、テスト4ケース

**設計パターン:**

1. **対話的初期化 + 個別操作の両立**
   - `team init`: 対話的にまとめてセットアップ
   - `team add/remove`: 個別に追加・削除
   - ユースケースに応じて使い分け可能

2. **プロジェクトローカル設定の分離**
   - `SaveToProject()` / `LoadProjectConfig()` を新設
   - グローバル設定（`~/.maxam/config.yaml`）とプロジェクト設定（`.maxam/config.yaml`）を明確に分離
   - 既存の`Load()` / `Save()`に影響を与えない設計

3. **存在しない場合のデフォルト値**
   ```go
   if os.IsNotExist(err) {
       return &Config{Version: "1"}, nil
   }
   ```
   - 設定ファイルがなくても動作する（初回利用時に自動生成）

4. **デフォルトエージェントの自動管理**
   - 最初に追加されたメンバーを自動でdefaultに設定
   - 削除時にdefaultが消えたら次のメンバーに自動更新
   - ユーザーが明示的に管理しなくても動作する

**ハードコード禁止規約への適合:**
- 人名・チーム名は全て設定ファイルから読み込み
- コード内にハードコードされた固有名詞なし
- 規約追加と同時にそれに沿った実装が入った好例

**チームフロー:**
- レビュー → LGTM → GitHubアカウント制約でApprove不可 → オーナー確認 → マージ
- 差し戻しゼロ、確認1回で完了

#### 設定フィールド追加の好例（PR #119より）

**変更規模:** 3ファイル、+106/-3行、テスト6ケース追加

**設計パターン:**

1. **オプショナルフィールドの追加**
   ```go
   type AgentConfig struct {
       // ...既存フィールド
       Color string `yaml:"color,omitempty"` // hex color code
   }
   ```
   - `omitempty`で後方互換性を維持
   - 未設定時は空文字（ゼロ値）

2. **フォールバックパターンの適用**
   ```go
   func (m *tuiModel) getAgentStyle(name string) lipgloss.Style {
       // 1. 設定から色を取得
       if m.config != nil {
           if color := m.config.GetAgentColor(name); color != "" {
               return lipgloss.NewStyle().Foreground(lipgloss.Color(color)).Bold(true)
           }
       }
       // 2. ハードコード色にフォールバック
       switch name { ... }
   }
   ```
   - 設定優先、なければデフォルト値
   - 既存動作を壊さない安全な拡張

3. **設定取得メソッドの追加**
   ```go
   func (c *Config) GetAgentColor(name string) string
   ```
   - 単一責任: 名前から色を引くだけ
   - nilチェック不要（呼び出し側で`config != nil`を確認）

**テスト設計:**
- `TestAgentConfigColor`: フィールドの有無を確認（2ケース）
- `TestGetAgentColor`: 取得ロジックを網羅（4ケース）
  - 色設定あり / 別の色 / 空文字 / 存在しないエージェント

**既存パターンとの関連:**
